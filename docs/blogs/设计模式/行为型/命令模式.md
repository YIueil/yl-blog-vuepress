# 命令模式（Command Pattern）

## 示例

用户通过遥控器控制空调、风扇、电灯等设备，只需按下按钮即可触发开/关等操作，而无需关心设备内部复杂的电路或执行逻辑。

## 设计思想

将“请求”封装成独立的命令对象，使请求发起方（Invoker，如遥控器）与请求接收方（Receiver，如电视、电灯）解耦。Invoker 只需调用命令对象的 `execute()`，具体由哪个 Receiver 执行、如何执行，都封装在 ConcreteCommand 中。

## 核心角色

- **Command**：命令接口，声明 `execute()`（以及可选的 `undo()`）；
- **ConcreteCommand**：具体命令，持有 Receiver 引用，负责将请求委托给 Receiver；
- **Receiver**：真正执行操作的对象；
- **Invoker**：调用者，持有并触发命令；
- **Client**：创建 Receiver 和 ConcreteCommand，并将它们装配到 Invoker。

## 在 JDK 和 Spring 中的应用

- **JDK**
  - `Runnable` / `Callable` 相当于 ConcreteCommand；
  - `Thread`、`Executor`、`ExecutorService` 相当于 Invoker；
  - Swing 中的 `ActionListener`、`javax.swing.undo.UndoableEdit` 也是典型应用。

- **Spring**
  - `CommandLineRunner` / `ApplicationRunner`：Spring Boot 启动时由容器统一执行；
  - `TaskExecutor`：将任务提交与执行解耦；
  - Spring MVC 的 `DispatcherServlet` + `HandlerAdapter`：请求分发器作为 Invoker，Controller 作为具体命令；
  - Spring Integration 的 `MessageHandler`、Spring State Machine 的 `Action` 等。

## 使用总结

1. **优点**
   - 请求被封装为对象，调用者与执行者完全解耦；
   - 天然支持 `undo` / `redo`，也便于实现命令队列、日志记录、事务回滚、宏命令等；
   - 新增 Receiver 或命令时，只需扩展具体类，符合开闭原则。

2. **注意事项**
   - 命令类过多时可能造成“类爆炸”，可通过参数化命令、函数式接口、通用命令类或宏命令来缓解；
   - 如果每个命令都很简单，直接方法调用即可，不必强行使用命令模式，避免过度设计。
